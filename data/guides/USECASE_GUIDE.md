# USECASE 작성 가이드

이 문서는 USECASE를 깎을 때 따르는 절차다.
USECASE는 SPEC을 기반으로 작성된다.
사용자는 결정하고, 작성 보조자는 묻고 문서화한다.

## 0. USECASE의 본질

USECASE는 SPEC의 계약이 정상적으로 사용되는 흐름을 사용자 관점과 시스템 관점 두 층으로 기록한 문서다.

> **USECASE = "사용자가 의도한 목적을 달성하는 정상 흐름" + "그것이 어떤 계약 호출 순서로 일어나는가"**

USECASE는 다음 두 가지를 동시에 만족해야 한다:
1. 사람이 읽고 "이 시스템이 누구의 무엇을 어떻게 해주는가"를 이해할 수 있다.
2. LLM이 읽고 어떤 계약을 어떤 순서로 호출하는 코드를 생성할 수 있다.

## 1. 기본 자세

- USECASE는 SPEC의 계약 ID(C1, C2 등)를 직접 참조한다. SPEC 없이 USECASE를 쓰지 않는다.
- 정상 흐름만 다룬다. 실패·예외·경계는 EDGECASE의 영역.
- USECASE는 EDGECASE를 참조하지 않는다. 둘은 모두 SPEC을 통해 간접 연결된다.
- 사용자 시나리오 단계 수와 계약 실행 단계 수는 같지 않아도 된다.
- 한 USECASE = 한 사용자 목적. 두 목적이면 두 USECASE로 분리.
- USECASE 작성 중 SPEC의 누락·모호함이 발견되면 SPEC 수정 절차로 돌아간다.

## 2. 단계별 진행 (게이트 방식)

### 1단계 — 목적 식별
질문:
- 이 USECASE에서 사용자는 무엇을 달성하려 하는가? (한 문장)
- 어떤 SPEC의 어떤 계약이 관여하는가?

통과 기준:
- 목적이 한 문장으로 표현됨
- 관련 SPEC과 계약 ID가 명시됨

### 2단계 — 행위자와 사전 조건
질문:
- 누가 이 흐름을 시작하는가? (역할·권한)
- 시작되기 전 무엇이 참이어야 하는가?

통과 기준:
- 행위자가 ROOT_SPEC personas 또는 시스템 역할 중 하나로 매핑됨
- 사전 조건이 검증 가능한 형태 (인증 상태, 데이터 존재 등)

### 3단계 — 사용자 시나리오
사용자 관점의 자연어 단계.

질문:
- 사용자가 어떤 행동을 하는가?
- 시스템이 사용자에게 무엇을 보여주는가?

통과 기준:
- 단계마다 행위자가 명확 (사용자 / 시스템)
- 구현 디테일 없음 ("DB에 저장한다" 같은 표현 금지)

### 4단계 — 계약 실행
시스템 관점의 계약 호출 순서.

질문:
- SPEC의 어떤 계약이 어떤 순서로 호출되는가?
- 각 호출의 입력은 어디서 오는가? (사용자 입력, 이전 호출 결과, 컨텍스트)
- 각 호출의 출력은 어떻게 사용되는가?

통과 기준:
- 모든 단계가 SPEC의 계약 ID를 참조 (자유 동작 금지)
- 입력·출력의 흐름이 추적 가능
- 이 USECASE에서 사용된 계약이 frontmatter `contracts`와 일치

### 5단계 — 사후 조건
질문:
- 흐름 완료 후 무엇이 참인가?
- SPEC의 어떤 불변식과 연결되는가?

통과 기준:
- 사후 조건이 검증 가능한 형태
- 사후 조건이 SPEC 불변식과 관련 있다면 해당 ID(I1, I2)가 인용됨. 관련 불변식이 없으면 생략 가능.

## 3. 빈틈 패턴 (즉시 지적)

| 패턴 | 문제 | 대응 |
|---|---|---|
| 계약 ID 참조 없는 단계 | SPEC과 단절 | C1, C2 등 명시 강제 |
| 실패·예외 흐름 포함 | EDGECASE 영역 침범 | 분리 |
| 구현 디테일 ("DB 저장", "API 호출") | 계층 위반 | 계약 호출로 환원 |
| 사용자 시나리오·계약 실행 중 한쪽만 있음 | 두 층 구조 위배 | 누락 층 작성 |
| 두 목적이 한 USECASE에 섞임 | 분해 부족 | USECASE 분리 |
| 사후 조건 없음 | 완료 시점 불명확 | 검증 가능한 사후 조건 작성 |
| 행위자 모호 | 권한·시작점 불명확 | 행위자 명시 |

## 4. 검증 체크리스트

- [ ] frontmatter에 id, title, spec_ref, contracts, status가 채워짐
- [ ] 목적이 한 문장으로 표현됨
- [ ] 행위자가 명시됨
- [ ] 사전 조건과 사후 조건이 검증 가능한 형태
- [ ] 사용자 시나리오와 계약 실행 두 층이 모두 존재
- [ ] 모든 계약 실행 단계가 SPEC의 계약 ID를 참조
- [ ] 사용된 계약이 frontmatter `contracts`와 일치
- [ ] 사후 조건이 SPEC 불변식과 관련 있다면 해당 ID가 인용됨
- [ ] 빈틈 패턴 7종 발견되지 않음

## 5. 수정 원칙

- 수정 전 영향 범위 산출:
  - 이 USECASE를 참조하는 ISSUE
- SPEC의 계약이 변경되면 이 USECASE도 재검토 대상.
- 수정 후 검증 체크리스트 재실행.
- 폐기 시 `status: deprecated` 표시. 본문 잔존. 소속 SPEC major 변경 시 정리.

## 6. 작성 규칙

- 정보 부족 섹션은 비우지 말고 "열린 질문"으로 분리한다.
- 사용자 결정 없이 임의로 채우지 않는다.
- 모든 결정은 사용자 발화, ROOT_SPEC, 또는 SPEC에서 인용 가능해야 한다.
- SPEC과 충돌하면 USECASE를 고치지 말고 SPEC 수정 절차로 돌아간다.
