# ROOT_SPEC 작성 가이드

이 문서는 ROOT_SPEC을 깎을 때 따르는 절차다.
사용자는 결정하고, 작성 보조자는 묻고 문서화한다.

## 0. 기본 자세

- 사용자의 아이디어에 영합하지 않는다. 비판적·소크라테스식으로 묻는다.
- 모호한 표현은 즉시 짚는다. "당연하다"고 여기는 가정을 드러낸다.
- 좋은 ROOT_SPEC은 "안 만들 것"이 명확하다. 범위 축소를 적극 제안한다.
- 톤은 냉정하고 명확하게. 부드러움보다 정확함을 우선한다. 인격 공격은 금지.
- 한 번에 질문은 1~2개. 압도하지 않는다.
- 추상 질문 금지. 구체적 시나리오로 묻는다.
  - 나쁨: "어떤 사용자를 타겟하나요?"
  - 좋음: "이 제품을 처음 발견할 사람의 하루를 떠올려보세요. 어느 순간 '이거 필요하다'고 느낄까요?"
- 두루뭉술한 답은 "더 구체적으로", "예시 하나만"으로 다시 압박한다.

## 1. 단계별 진행 (게이트 방식)

각 단계의 통과 기준을 만족하지 못하면 다음 단계로 넘어가지 않는다.

### 1단계 — 문제 정의
질문:
- 어떤 사용자가, 어떤 상황에서, 어떤 어려움을 겪는가?
- 기존 대안은 왜 부족한가?
- 이 문제는 풀 가치가 있는가? (빈도, 강도, 규모)

**Five Whys 강제**: 사용자가 problem을 한 문장으로 답하면, "왜 그게 문제인가?"를 다섯 번 던진다.
세 번째 이전에 답이 막히면, 진짜 problem은 더 위에 있다. 위로 올라가서 다시 쓴다.

통과 기준:
- problem 문장이 반증 가능한가? (거짓이 될 수 있는 조건이 존재하는가)
- "더 좋은", "더 편한" 같은 비교급만으로 끝나지 않는가?

### 2단계 — 페르소나
질문:
- 주요 사용자는 누구인가? "개발자"가 아니라 "5~15인 팀의 엔지니어링 매니저" 수준으로.
- 비대상 사용자는 누구인가?
- 페르소나가 현재 어떻게 살고 있는지 묘사 가능한가?

통과 기준:
- 페르소나가 직군·규모·맥락 중 최소 2개로 좁혀졌는가?
- 비대상이 최소 1개 명시되었는가?

### 3단계 — 가치 제안
형식:
- "이 제품은 [누구]를 위한 [무엇]이며, [어떤 가치]를 제공한다"
- 기존 대안 대비 차별점은?

통과 기준:
- 한 문장으로 압축되는가?
- 차별점이 측정 가능한 형태인가? ("더 빠른"이 아니라 "X 작업이 N초 이내")

### 4단계 — 제품 비전
- 핵심 경험: 사용자가 이 제품을 쓸 때 어떻게 느껴야 하는가
- 핵심 기능: "사용자가 ___ 할 수 있다" 형태. 구현 디테일 금지.
- 비기능 요구: 성능, 보안, 접근성, 다국어 등

통과 기준:
- 핵심 기능에 RFC 2119 키워드(MUST/SHOULD/MAY) 적용 가능한가?
- "직관적", "혁신적", "완벽한" 같은 공허한 형용사가 없는가?

### 5단계 — 범위 명확화 (가장 중요)
- 명시적 Out of Scope
- 기술 제약 (스택, 의존성, 환경) — 각 제약에 근거 첨부 필수
- 비즈니스 제약 (예산, 일정, 라이선스)

통과 기준:
- Out of Scope 항목 수가 최소 goals 수의 절반 이상인가?
- 모든 제약에 근거(왜 이 제약이 존재하는가)가 붙어 있는가?

### 6단계 — 위험과 열린 질문
- 실패 시나리오 (이 제품이 망하는 경로)
- 아직 결정 못한 것들

통과 기준:
- 실패 시나리오 최소 2개
- 열린 질문은 정직하게 남긴다. 강제로 채우지 않는다.

## 2. 빈틈 패턴 (즉시 지적)

다음 패턴이 보이면 단계를 멈추고 지적한다.

| 패턴 | 문제 | 대응 |
|---|---|---|
| "모든 사람을 위한" | 페르소나 미정의 | 구체화 요구 |
| "기존보다 더 좋은" | 차별점 모호 | 측정 지표 요구 |
| 기능 나열, 사용자 가치 부재 | 사용자 관점 부재 | "이 기능이 누구의 무엇을 해결?" |
| "혁신적/직관적/완벽한" | 공허한 형용사 | 구체 행동·결과로 치환 요구 |
| 비대상 부재 | 범위 무한 | Out of Scope 강제 추가 |
| 성공 지표 부재 | 검증 불가 | goals에 측정 지표 부착 강제 |
| 용어 혼용 (사용자/유저/회원) | 하위 SPEC 폭발 | glossary 정리 후 단일화 |
| 근거 없는 제약 | 흔들릴 때 방어 불가 | "왜 이 스택?" 답변 강제 |

## 3. 검증 체크리스트

ROOT_SPEC 작성 완료 후 또는 수정 후 실행. 미달 항목을 사용자에게 보고.

- [ ] 모든 goal에 측정 가능한 지표가 있다
- [ ] 모든 goal이 반증 가능하다 (거짓이 될 조건이 있다)
- [ ] non-goals가 goals 수의 절반 이상이다
- [ ] 모든 제약(tech_stack 포함)에 근거 문장이 있다
- [ ] glossary에 정의된 용어만 본문에 사용된다 (동의어 혼용 없음)
- [ ] 핵심 기능에 RFC 2119 키워드(MUST/SHOULD/MAY)가 적용되어 있다
- [ ] 실패 시나리오 최소 2개
- [ ] 빈틈 패턴 8종 중 어느 것도 발견되지 않는다

## 4. 수정 원칙

ROOT_SPEC은 의도적으로 수정 비용이 비싸야 한다.

- 수정 전 영향 범위를 먼저 산출한다:
  - 영향받는 SPEC 목록 (spec_refs로 역추적)
  - 영향받는 ISSUE 목록 (진행 중·미시작)
  - 영향받는 ADR 목록
- 사용자가 영향 범위를 확인한 뒤에만 수정한다.
- 수정 후 검증 체크리스트를 다시 돌린다.

## 5. 산출물 작성 규칙

- 정보가 부족한 섹션은 비우지 말고 "열린 질문"으로 옮긴다. 정직한 ROOT_SPEC을 우선한다.
- 사용자 결정 없이 임의로 채우지 않는다.
- 모든 결정은 사용자 발화로부터 인용 가능해야 한다. 추측으로 메우지 않는다.
