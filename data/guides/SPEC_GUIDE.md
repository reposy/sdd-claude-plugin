# SPEC 작성 가이드

이 문서는 SPEC을 깎을 때 따르는 절차다.
SPEC은 ROOT_SPEC을 기반으로 사용자와의 합의에 의해 작성된다.
사용자는 결정하고, 작성 보조자는 묻고 문서화한다.

## 0. SPEC의 본질

SPEC은 "무엇을 만드는가"의 정의다. 코드는 SPEC의 번역물이다.
따라서 SPEC의 품질은 다음 한 가지로 측정된다:

> **이 SPEC을 두 사람에게 따로 구현시켰을 때, 외부 행동·계약·범위가 수렴하는가?**

본질 결정론성이 SPEC의 유일한 기준이다. 표현의 다양성은 허용된다.
나머지 모든 규칙은 이 기준을 강제하기 위해 존재한다.

## 1. 기본 자세

- ROOT_SPEC에 없는 결정을 SPEC이 만들지 않는다. 충돌하면 ROOT_SPEC을 먼저 고친다.
- 모호함은 즉시 깎는다. "적절히", "필요시", "일반적으로" 같은 표현은 발견 즉시 지적.
- 구현 디테일은 SPEC에 두지 않는다. SPEC은 "무엇", 코드는 "어떻게".
- 단, 외부에서 관찰 가능한 행동(API 시그니처, 데이터 형식, 상태 전이)은 구현이 아니라 계약이므로 SPEC에 둔다.
- 한 SPEC은 한 도메인. 도메인을 넘어가면 SPEC을 쪼갠다. 작은 도메인이라도 합치지 않는다.
- USECASE/EDGECASE는 SPEC에 포함하지 않는다. SPEC 완료 후 별도 단계에서 작성한다.
- 한 번에 질문은 1~2개.

## 2. 단계별 진행 (게이트 방식)

각 단계의 통과 기준을 만족하지 못하면 다음 단계로 넘어가지 않는다.

### 1단계 — 도메인 경계 확정
질문:
- 이 SPEC이 다루는 범위는 어디까지인가?
- 다른 SPEC과의 경계는 어디인가?
- 어떤 SPEC에 의존하는가? (depends_on)
- 도메인을 한 줄로 요약하면? (summary — specs/INDEX 카탈로그에 노출됨)

통과 기준:
- 도메인 이름 한 단어로 표현 가능
- 의존 SPEC이 명시됨 (없으면 없다고 명시)
- ROOT_SPEC의 어느 goal/feature를 담당하는지 매핑됨
- summary 한 줄이 작성됨 (도메인 경계와 일관)

### 2단계 — 용어 정의 (Glossary)
ROOT_SPEC glossary에 없는 도메인 용어를 먼저 정의한다.

통과 기준:
- 본문에서 쓸 모든 도메인 명사가 정의됨
- ROOT_SPEC glossary와 충돌 없음
- 동의어 없음 (한 개념 한 단어)

### 3단계 — 계약 (Contracts)
외부에서 관찰 가능한 입출력 정의.

질문:
- 이 도메인이 외부에 제공하는 것은 무엇인가? (API, 이벤트, 데이터)
- 외부로부터 받는 것은 무엇인가?
- 각 계약의 입력·출력·실패 모드는?

통과 기준:
- 모든 계약에 입력 타입, 출력 타입, 실패 케이스 명시
- 계약 이름이 glossary 용어로만 구성됨

### 4단계 — 불변식 (Invariants)
이 도메인에서 항상 참이어야 하는 조건.

질문:
- 이 도메인의 데이터·상태에서 절대 깨지면 안 되는 규칙은?
- 그 규칙이 깨지면 어떻게 알 수 있는가? (검증 가능성)

통과 기준:
- 각 불변식이 검증 가능한 형태 (테스트로 표현 가능)
- 추상적 표현("일관성 유지") 금지

### 5단계 — 상태 전이 (해당 시)
도메인이 상태를 가지면 전이도를 정의한다.

질문:
- 어떤 상태들이 있는가?
- 어떤 사건이 어떤 전이를 일으키는가?
- 불가능한 전이는?

통과 기준:
- 모든 상태와 전이가 열거됨
- 불가능한 전이 명시 (안 적으면 가능하다고 가정됨)
- 상태 전이를 건너뛴 경우, 그 근거가 명시됨 (예: "이 도메인은 stateless")

## 3. 빈틈 패턴 (즉시 지적)

| 패턴 | 문제 | 대응 |
|---|---|---|
| "적절히 처리" | 동작 미정의 | 구체 동작 요구 |
| "필요시", "일반적으로" | 조건 미정의 | 조건 명시 요구 |
| 구현 코드·라이브러리 이름 | 계층 위반 | 외부 관찰 가능한 행동으로 환원 |
| 동의어 (사용자/유저/회원) | 본질 결정론성 파괴 | glossary 정리 |
| 실패 모드 누락 | EDGECASE 식별 불가 | 실패 케이스 강제 열거 |
| 불변식이 추상적 | 검증 불가 | 테스트 가능한 형태로 |
| 다른 SPEC 영역 침범 | 도메인 경계 흐림 | 분리 또는 의존 명시 |
| 상태 있으나 전이도 없음 | 행동 비결정성 | 전이도 작성 강제 |
| 작은 도메인을 다른 도메인과 합침 | 일관성 파괴 | 분리 |

## 4. 검증 체크리스트

SPEC 작성 완료 후 또는 수정 후 실행. 미달 항목 보고.

- [ ] depends_on이 명시됨 (또는 명시적으로 없음)
- [ ] ROOT_SPEC의 goal/feature와 매핑됨
- [ ] 본문에 쓰인 모든 도메인 명사가 glossary에 있음
- [ ] 동의어 없음
- [ ] 모든 계약에 입력·출력·실패 케이스가 있음
- [ ] 모든 불변식이 검증 가능한 형태
- [ ] 상태가 있으면 전이도가 있음. 불가능한 전이도 명시
- [ ] 상태 전이를 생략한 경우 사유가 명시됨
- [ ] 빈틈 패턴 9종 발견되지 않음
- [ ] 구현 디테일(라이브러리, 알고리즘 선택) 없음
- [ ] USECASE/EDGECASE가 SPEC 본문에 포함되어 있지 않음
- [ ] frontmatter에 status, version, summary, depends_on이 채워짐

## 5. 수정 원칙

SPEC은 ROOT_SPEC보다는 가볍지만 ISSUE보다는 무겁다.

- 수정 전 영향 범위를 먼저 산출:
  - 의존하는 다른 SPEC (역방향 depends_on)
  - 영향받는 USECASE / EDGECASE
  - 영향받는 ISSUE (진행 중·미시작)
  - 영향받는 ADR
- 사용자가 영향 범위를 확인한 뒤에만 수정.
- 수정 후 검증 체크리스트 재실행.
- SPEC 버전을 올린다 (semver):
  - 계약 변경 = major
  - 계약 추가 = minor
  - 명료화·오타·glossary 보완 = patch
- status가 active였다면 코드와의 정합성 검사 필요 → drift 보고.

### ID 관리
- 계약(C1, C2...), 불변식(I1, I2...) 등 SPEC 내 ID는 한 번 부여되면 영구. 같은 SPEC 안에서 재활용하지 않는다.
- 계약·불변식이 삭제되면 deprecated로 표시만 남기고 본문에 잔존시킨다.
- major 버전 변경 시 deprecated 항목을 정리할 수 있다. 정리 시 외부 참조(USECASE, EDGECASE, ISSUE)도 함께 끊고, 사유를 ADR에 남긴다.

## 6. 작성 규칙

- 정보 부족 섹션은 비우지 말고 "열린 질문"으로 분리한다.
- 사용자 결정 없이 임의로 채우지 않는다.
- 모든 결정은 사용자 발화 또는 ROOT_SPEC에서 인용 가능해야 한다.
- ROOT_SPEC과 충돌하면 SPEC을 고치지 말고 ROOT_SPEC 수정 절차로 돌아간다.
- USECASE/EDGECASE 작성 단계에서 SPEC의 한계가 드러나면 SPEC 수정 절차로 돌아간다.
