# PLAN 작성 가이드

이 문서는 PLAN을 조립할 때 따르는 절차다.
PLAN은 사용자가 깎지 않는다. LLM이 관련 문서를 자동 추적·조립한다. 사용자는 검토자.

## 0. PLAN의 본질

PLAN은 한 TASK의 구현 계획서다. TASK("무엇을 할지")와 코드("어떻게 됐는지") 사이의 다리("어떻게 옮길지")를 정의한다.

> **이 PLAN대로 코드 작성했을 때, TASK가 충실히 반영되고 모든 근거 SPEC/USECASE/EDGECASE/ADR과 일관되는가?**

추적 가능성이 PLAN의 유일한 기준이다.
나머지 모든 규칙은 이 기준을 강제하기 위해 존재한다.

## 1. 기본 자세

- LLM이 자동 조립한다. 사용자가 한 줄씩 깎지 않는다. 사용자는 검토·승인.
- 모든 결정·파일·변경에는 근거 문서 인용이 따른다. 자유 추측 금지.
- 수정 대상 파일은 구체 경로로 적는다. "auth 관련 파일들" 같은 추상 금지.
- 코드 본문은 적지 않는다. 시그니처·구조 수준까지만. 코드는 메인 Claude Code의 책임.
- 한 PLAN은 한 TASK. 여러 TASK를 묶지 않는다.
- 추적 범위는 명시한다. 어디까지 보고 어디는 무시했는지 투명하게.

## 2. 단계별 진행 (조립 절차)

### 1단계 — TASK 읽기
- TASK frontmatter의 id, title, primary_kind, depends_on 확인.
- TASK 본문에서 작업 범위·완료 조건 추출.
- 통과 기준: TASK가 명확함. 모호하면 PLAN 조립 중단, TASK 갱신 권유.

### 2단계 — 상위 ISSUE 읽기
- TASK가 속한 ISSUE의 본문 읽기.
- ISSUE의 "관련 SPEC", "다루지 않는 것" 확인.
- 통과 기준: ISSUE의 범위와 TASK가 정합.

### 3단계 — 관련 SPEC 추적
- ISSUE에서 인용한 SPEC들 모두 읽기 (Contract 부분 집중).
- 외부 행동·계약·불변식 추출.
- 통과 기준: TASK가 영향을 주는 모든 Contract 식별 완료.

### 4단계 — USECASE/EDGECASE 추적
- 각 SPEC의 usecases/, edgecases/ 디렉터리에서 관련 시나리오 추적.
- TASK 범위와 겹치는 시나리오만 인용 (전체 인용 금지).
- 통과 기준: 정상 흐름 + 실패 경로 모두 식별.

### 5단계 — ADR 식별
- adrs/INDEX.md에서 관련 SPEC·도메인 태그 검색.
- 영향받는 ADR이 있으면 인용.
- 통과 기준: 결정과 충돌하는 PLAN을 만들지 않음.

### 6단계 — 수정 대상 파일 목록 작성
- 각 파일별: 경로, 변경 종류(신규/수정/삭제), 한 줄 요약.
- 시그니처·타입 수준까지만. 함수 본문 작성 금지.
- 통과 기준: 모든 파일 경로가 구체적. 새 파일이면 신규 표시 명확.

### 7단계 — 부수 변경 명시
- 새 의존성 (npm/pip 등)
- 환경 변수 추가/변경
- DB 스키마 마이그레이션
- 설정 파일 변경
- 통과 기준: 누락 없이 모두 표시. 진행 중 새 의존성 발견되면 흐름 중단·PLAN 재조립.

### 8단계 — 검증 방법 명시
- 어떤 테스트를 추가/수정할지 (USECASE·EDGECASE 시나리오 기반).
- 수동 검증 절차 (필요 시).
- 통과 기준: TASK 완료 조건이 어떤 테스트로 확인되는지 명확.

### 9단계 — 사용자 검토 요청
- PLAN 본문 표시.
- 사용자: 승인 / 수정 요구 / 폐기 중 선택.
- 통과 기준: 사용자 명시 승인.

## 3. 빈틈 패턴

| 패턴 | 문제 | 처리 |
|---|---|---|
| 근거 인용 누락 | "왜 이렇게 결정?" 답 없음 | 인용 강제, 인용 없는 결정은 PLAN에 들어가지 못함 |
| 수정 파일이 추상적 | 코드 작성 시 본질 결정론성 파괴 | 구체 경로 강제 |
| 코드 본문 작성 | 계층 위반 (PLAN ≠ 코드) | 시그니처 수준으로 환원 |
| 새 의존성 누락 | 진행 중 발견 시 흐름 중단 | 7단계 강제 점검 |
| 검증 방법 누락 | TASK 완료 판정 불가 | 8단계 강제 점검 |
| 여러 TASK 묶음 | 한 PLAN = 한 TASK 원칙 위반 | TASK별로 분리 |
| 추적 범위 불명 | 빠진 근거가 있는지 알 수 없음 | "추적한 문서 / 추적 안 한 것" 명시 |

## 4. 검증 체크리스트

- [ ] frontmatter의 task_ref가 실제 TASK ID와 일치하는가?
- [ ] 인용한 SPEC/USECASE/EDGECASE/ADR이 모두 ID로 명시되었는가?
- [ ] 수정 대상 파일이 모두 구체 경로인가?
- [ ] 코드 본문이 없는가? (시그니처·구조 수준까지만)
- [ ] 새 의존성·환경·DB 변경이 명시되었는가?
- [ ] 검증 방법이 TASK 완료 조건과 매핑되는가?
- [ ] 추적 범위가 명시되었는가? (본 문서 / 안 본 것)
- [ ] 한 PLAN에 한 TASK만 다루는가?

## 5. 수정 원칙

PLAN은 직접 수정하지 않는다. 다음 경우 폐기 후 재조립:

- TASK가 변경됨 → PLAN 재조립
- TASK가 인용한 SPEC이 변경됨 → 영향받는 모든 PLAN 재조립
- 진행 중 새 의존성·범위 변경 발견 → 현 PLAN 폐기, 사용자 보고 후 재조립

수정 대신 재조립하는 이유: PLAN은 *현 시점의 추적 결과*다. 부분 수정하면 추적 결과의 일관성이 깨진다.

상태 변화: `draft` → `reviewed` → `executed`. `executed` 후엔 PLAN을 변경하지 않음 (이력 보존). 변경 필요 시 새 PLAN 생성.

## 6. 작성 규칙

### 형식
- 표 위주. 산문 최소화.
- ID 형식: `PLAN-XX` (대응 `TASK-XX`와 같은 번호).
- frontmatter 필수.

### frontmatter 필드
- `id`: PLAN-XX
- `task_ref`: TASK-XX (대응 TASK ID)
- `date`: 조립일
- `status`: draft | reviewed | executed
- `references`: 인용한 모든 ID 배열 (SPEC, UC, EC, ADR)

### 본문 섹션 (고정 순서)
1. 요약 (한 문단)
2. TASK 인용 (TASK 본문 한 줄 요약)
3. 근거 추적 (표: ID, 종류, 인용 사유)
4. 수정 대상 파일 (표: 경로, 변경 종류, 요약)
5. 부수 변경 (의존성·환경·DB)
6. 검증 방법
7. 추적 범위 (본 문서 / 안 본 것)
8. 위험·열린 질문

### 자동 생성 표시
- 본문 상단에 `> 이 문서는 sdd-plan으로 자동 조립되었다. 직접 수정 금지.`
- 사용자 검토는 frontmatter의 status 변경으로 표시.
