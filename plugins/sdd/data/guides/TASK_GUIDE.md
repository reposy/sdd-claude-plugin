# TASK 작성 가이드

이 문서는 TASK를 깎을 때 따르는 절차다.
TASK는 ISSUE를 기반으로 작성된다.
LLM은 묻고 문서화하고, 사용자는 결정한다.

## 0. TASK의 본질

TASK는 ISSUE를 코드로 실제로 옮기는 작업의 단위다.

> **TASK = 한 PR로 끝나는, ISSUE의 부분 작업**

TASK는 다음을 만족한다:
1. 항상 ISSUE에 종속된다. ISSUE 없이 TASK 없음.
2. 한 PR에 대응한다. PR 단위가 TASK 단위.
3. ISSUE의 만족 조건 일부를 충족시키는 책임을 진다.
4. SPEC 계층(SPEC, USECASE, EDGECASE)을 직접 참조하지 않는다. ISSUE를 통해 간접 참조.
5. SPEC 외 작업(리팩터링, 인프라, chore)도 흡수 가능.
6. 같은 ISSUE 내 다른 TASK에 의존할 수 있다.

## 1. 작성 원칙

- **LLM이 작성한다.** 본문·frontmatter는 LLM이 채운다.
- **사용자는 결정자다.** LLM은 묻고 사용자는 답한다.
- **상위 문서(ISSUE)에 명시된 것은 그대로 활용한다.** 사용자에게 다시 묻지 않는다.
- **추론 금지.** 빈 자리는 비우거나 묻는다.
- **본문은 작업 중 갱신될 수 있다.** 단 갱신은 사용자 결정을 동반한다. 임의 갱신 금지.
- 한 번에 질문은 1~2개.

## 2. 기본 자세

- TASK는 ISSUE만 참조한다. SPEC 계층 직접 참조 금지.
- 한 TASK = 한 PR. 한 TASK가 여러 PR로 갈라지면 TASK를 분리.
- TASK는 작업 중 코드와 상호작용하는 문서다. 작성 후 닫혀 있는 명세가 아니라 진행 중 살아 있는 작업 노트.
- TASK 진행 중 사용자 결정이 발생하면 ADR 작성 트리거 검토 (4절 참조).
- 같은 ISSUE 내 TASK 간 순서·병렬성은 `depends_on`으로 표현한다.

## 3. 단계별 진행 (게이트 방식)

### 1단계 — 부모 ISSUE 확인
질문:
- 이 TASK는 어떤 ISSUE에 속하는가?
- 그 ISSUE의 만족 조건 중 어떤 부분을 이 TASK가 다루는가?

통과 기준:
- `parent_issue` 명시
- ISSUE 만족 조건과의 매핑이 본문에 표현 가능

### 2단계 — 종류 식별
질문:
- 이 TASK의 주된 성격은 무엇인가? (`implementation | refactor | infra | chore`)
- 부수적 성격이 있는가?

통과 기준:
- `primary_kind`가 4종 중 하나로 결정됨
- 부수적 성격이 있으면 `secondary_kinds` 채움. 없으면 생략.

### 3단계 — 변경 대상 식별
질문:
- 어떤 파일·모듈을 수정/생성/삭제하는가?

통과 기준:
- 변경 대상 목록이 본문에 명시됨
- 10개 초과 시 사용자에게 확인. 분리할지, 그대로 진행할지 사용자 결정.
- 초기 환경 설정·의존성 추가 등으로 자연스럽게 많은 경우는 사용자 판단으로 그대로 진행 가능.

### 4단계 — 의존성 식별
질문:
- 같은 ISSUE 내에서 먼저 끝나야 할 다른 TASK가 있는가?

통과 기준:
- `depends_on`이 명시됨 (없으면 빈 배열)
- 의존성은 같은 ISSUE 내 TASK 간에만 표현. 다른 ISSUE의 TASK는 참조하지 않음 (ISSUE의 depends_on이 그 역할).

### 5단계 — 만족 조건
질문:
- 이 TASK가 닫힐 자격이 되는 조건은 무엇인가?
- ISSUE의 어떤 만족 조건을 충족시키는가?

통과 기준:
- 모든 만족 조건이 검증 가능한 형태
- ISSUE의 만족 조건과 매핑됨 (또는 매핑되지 않는 이유 명시 — 예: refactor TASK)
- 종류별 만족 조건이 적합:
  - `implementation`: USECASE/EDGECASE 충족, 테스트 통과
  - `refactor`: 기존 테스트 통과, 외부 행동 변화 없음
  - `infra`: 환경 구축·배포 동작 확인
  - `chore`: 의존성 갱신·도구 설정 완료

## 4. ADR 작성 트리거

TASK 진행 중 사용자 결정이 발생했을 때, 다음 중 하나라도 해당하면 ADR 작성을 사용자에게 제안한다.

1. 대안이 둘 이상 명시적으로 검토됨 (사용자가 "A vs B"를 고민함).
2. 결정이 SPEC 또는 ROOT_SPEC을 변경시킴.
3. 결정이 다른 TASK·ISSUE의 진행 방식을 바꿈.
4. 결정이 ROOT_SPEC의 제약(tech_stack, 비기능 요구)을 추가/수정함.
5. 결정이 보류·기각된 대안과 그 사유를 포함함.
6. 결정이 프로젝트 가치관·우선순위·철학을 표현함.

다음 결정은 ADR 작성하지 않는다:
- 변수명·함수명 등 명명
- 파일 위치·디렉터리 구조 (관행 따른 경우)
- 한 TASK 안에서만 의미 있는 구현 디테일
- 합의된 가이드대로 진행한 것

ADR 작성 여부는 사용자에게 확인. 추론으로 자동 결정 금지.

## 5. 빈틈 패턴 (즉시 지적)

| 패턴 | 문제 | 대응 |
|---|---|---|
| `parent_issue` 비어 있음 | 부모 부재 | ISSUE 식별 강제 |
| SPEC/USECASE/EDGECASE 직접 참조 | 계층 위반 | ISSUE를 통해 간접 참조 |
| 만족 조건이 추상적 | 닫힐 시점 불명확 | 검증 가능한 형태로 |
| 한 TASK가 여러 PR로 갈라짐 | 단위 위반 | TASK 분리 |
| 변경 대상 미명시 | 범위 모호 | 파일·모듈 목록 명시 |
| 종류와 만족 조건 불일치 | 검증 부적합 | 종류에 맞는 조건으로 |
| 본문 임의 갱신 | 추론 발생 | 사용자 결정 동반 갱신만 |
| 다른 ISSUE의 TASK를 depends_on에 인용 | 계층 위반 | ISSUE의 depends_on으로 표현 |

## 6. 검증 체크리스트

- [ ] frontmatter에 id, parent_issue, primary_kind, depends_on, status가 채워짐
- [ ] 부모 ISSUE가 존재함
- [ ] 종류(primary_kind)가 4종 중 하나
- [ ] 변경 대상이 명시됨 (10개 초과 시 사용자 확인 완료)
- [ ] depends_on이 명시됨 (빈 배열 가능, 같은 ISSUE 내 TASK만)
- [ ] 모든 만족 조건이 검증 가능한 형태
- [ ] ISSUE 만족 조건과 매핑됨 (또는 매핑되지 않는 사유)
- [ ] SPEC 계층 직접 참조 없음
- [ ] 빈틈 패턴 8종 발견되지 않음

## 7. 수정 원칙

- TASK 본문은 작업 중 갱신될 수 있다.
- 갱신은 사용자 결정을 동반한다. 임의 갱신 금지.
- 만족 조건 추가·삭제는 부모 ISSUE의 만족 조건과의 정합성 확인 필요.
- 종류(kind)가 바뀌면 새 TASK로 분리 검토.
- 취소된 TASK는 파일 삭제.

## 8. PR 연결

- TASK는 한 PR에 대응.
- PR 생성 시 frontmatter `pr_url` 채움.
- PR 머지 시 `status: done`으로 갱신.
- PR이 split·squash되면 TASK도 그에 맞게 분리·통합.

## 9. 작성 규칙

- 정보 부족 섹션은 비우지 말고 "열린 질문"으로 분리.
- 사용자 결정 없이 임의로 채우지 않는다.
- 모든 결정은 사용자 발화 또는 부모 ISSUE에서 인용 가능해야 한다.
- ISSUE와 충돌하면 TASK를 고치지 말고 ISSUE 수정 절차로 돌아간다.
