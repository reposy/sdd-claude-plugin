# ISSUE 작성 가이드

이 문서는 ISSUE를 깎을 때 따르는 절차다.
ISSUE는 SPEC 계층(SPEC, USECASE, EDGECASE) 또는 ADR을 기반으로 작성된다.
LLM은 묻고 문서화하고, 사용자는 결정한다.

## 0. ISSUE의 본질

ISSUE는 SPEC 계층 또는 ADR을 코드로 옮기는 작업의 묶음 단위다.

> **ISSUE = "한 의미 단위의 구현 작업이 여기서 시작되어 여기서 끝난다"는 추적 단위**

ISSUE는 다음을 만족한다:
1. SPEC 계층(SPEC, USECASE, EDGECASE) 또는 ADR에서 파생된다. ROOT_SPEC은 직접 참조하지 않는다.
2. 한 ISSUE는 여러 TASK로 분해된다 (1:N).
3. ISSUE는 TASK를 직접 알지 않는다. TASK 추적은 디렉터리 INDEX가 한다.
4. GitHub Issue로 발신된다. 파일이 source of truth.

## 1. 작성 원칙

- **LLM이 작성한다.** 모든 본문·frontmatter는 LLM이 채운다.
- **사용자는 결정자다.** LLM은 묻고 사용자는 답한다.
- **상위 문서에 명시된 것은 그대로 활용한다.** 사용자에게 다시 묻지 않는다.
- **명시되지 않거나 모호한 것만 사용자에게 묻는다.**
- **추론 금지.** 빈 자리는 채우지 말고 비우거나 묻는다.
- 한 번에 질문은 1~2개.

## 2. 기본 자세

- ISSUE는 SPEC, USECASE, EDGECASE, ADR을 참조한다. ROOT_SPEC을 직접 참조하지 않는다.
- ISSUE 본문에 TASK ID를 인용하지 않는다. TASK는 디렉터리로만 연결된다.
- 한 ISSUE는 여러 상위 문서를 참조할 수 있다.
- ISSUE 작성 중 상위 문서의 누락·모호함이 발견되면 해당 문서 수정 절차로 돌아간다.

## 3. 단계별 진행 (게이트 방식)

### 1단계 — 출처 식별
질문:
- 이 ISSUE는 어떤 SPEC, USECASE, EDGECASE, ADR에서 파생되는가?

통과 기준:
- `spec_refs` 또는 `adr_refs` 중 최소 하나 이상 명시됨
- USECASE/EDGECASE를 다룬다면 해당 ID들도 명시됨

### 2단계 — 목적과 범위
- 목적: 이 ISSUE가 끝나면 무엇이 달라지는가 (한 문장)
- 범위: 다루는 것 / 다루지 않는 것

통과 기준:
- 목적이 한 문장으로 표현됨
- 다루는 것·다루지 않는 것이 명시됨
- 상위 문서에 명시된 정보로 채울 수 있는 부분은 자동 채움

### 3단계 — 완료 조건 (Acceptance)
질문:
- 이 ISSUE가 닫힐 자격이 되는 조건은 무엇인가?

통과 기준:
- 모든 완료 조건이 검증 가능한 형태
- USECASE/EDGECASE 참조 시 해당 ID 인용
- SPEC 계약·불변식과의 일치 여부 포함
- ADR에서 파생된 경우, ADR이 요구한 변경 사항이 조건에 반영됨

### 4단계 — 의존성 식별
질문:
- 먼저 끝나야 할 다른 ISSUE가 있는가?
- 외부 의존(인프라, 외부 API 등)이 있는가?

통과 기준:
- `depends_on`이 명시됨 (없으면 빈 배열)
- 외부 의존이 있으면 본문에 명시

### 5단계 — TASK 분해 가능성 검토
질문:
- 이 ISSUE가 5~10개 TASK로 분해 가능한가?

통과 기준:
- 5~10개 범위 내 분해 가능 → 통과
- 10개 초과 분해 → 사용자에게 확인. "권장 범위를 초과합니다. 그대로 두시겠습니까, 분리하시겠습니까?" 사용자 결정에 따름.
- 분해가 1~2개 → 사용자에게 확인. ISSUE 작게 유지할지, 인접 ISSUE에 흡수할지 사용자 결정.

분리·흡수의 최종 판단은 항상 사용자에게 있다. 추론으로 강제 진행 금지.

## 4. 빈틈 패턴 (즉시 지적)

| 패턴 | 문제 | 대응 |
|---|---|---|
| ROOT_SPEC을 직접 참조 | 계층 위반 | SPEC을 거쳐 참조 |
| `spec_refs`와 `adr_refs` 둘 다 비어 있음 | 출처 불명 | 출처 식별 강제 |
| 완료 조건이 추상적 | 닫힐 시점 불명확 | 검증 가능한 형태로 |
| TASK ID를 본문에 인용 | 결합 발생 | 인용 제거. INDEX가 추적 |
| 의존성 식별 없음 | 순서 모호 | depends_on 명시 |
| "다루지 않는 것" 누락 | 범위 불명확 | 명시 강제 |
| 상위 문서에 답이 있는데 사용자에게 질문 | 시간 낭비 | 자동 채움 |
| 빈 자리를 추론으로 채움 | 본질 결정론성 파괴 | 비우거나 묻기 |

## 5. 검증 체크리스트

- [ ] frontmatter에 id, title, depends_on, status가 채워짐
- [ ] `spec_refs` 또는 `adr_refs` 중 하나 이상이 비어 있지 않음
- [ ] USECASE/EDGECASE를 다루면 해당 refs가 채워짐
- [ ] 목적이 한 문장으로 표현됨
- [ ] 범위(다루는 것 / 다루지 않는 것)가 명시됨
- [ ] 모든 완료 조건이 검증 가능한 형태
- [ ] TASK 분해 가능성이 검토되고 사용자 결정이 반영됨
- [ ] 본문에 TASK ID 인용 없음
- [ ] depends_on이 명시됨 (빈 배열 가능)
- [ ] 빈틈 패턴 8종 발견되지 않음

## 6. 수정 원칙

- 수정 전 영향 범위 산출:
  - 이 ISSUE에 의존하는 다른 ISSUE
  - 이 ISSUE에 속한 TASK들 (INDEX로 확인)
  - 연결된 GitHub Issue
- 상위 문서(SPEC, USECASE, EDGECASE, ADR)의 변경으로 인한 ISSUE 수정은 변경 영향 분석을 동반.
- 파일 변경은 GitHub Issue에 반영 (단방향 발신).
- 수정 후 검증 체크리스트 재실행.
- 폐기 시 `status: closed` 또는 `status: cancelled`. 본문 잔존.

## 7. GitHub 동기화

ISSUE 파일이 source of truth.

- **파일 → GitHub** (발신): title, body, depends_on(이슈 링크), spec_refs(라벨 후보).
  - 파일이 변경되면 GitHub Issue도 갱신한다.
  - 파일이 새로 생기면 GitHub Issue를 생성하고 `gh_number`를 frontmatter에 기록한다.
- **GitHub → 파일** (수신): 없음.
  - GitHub에서 직접 변경된 내용(close, label 변경, comment 등)은 파일에 반영하지 않는다.
  - 파일의 status가 진실. GitHub state는 파일을 따른다.

## 8. 작성 규칙

- 정보 부족 섹션은 비우지 말고 "열린 질문"으로 분리.
- 사용자 결정 없이 임의로 채우지 않는다.
- 모든 결정은 사용자 발화 또는 상위 문서에서 인용 가능해야 한다.
- 상위 문서와 충돌하면 ISSUE를 고치지 말고 상위 문서 수정 절차로 돌아간다.
