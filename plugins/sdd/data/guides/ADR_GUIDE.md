# ADR 작성 가이드

이 문서는 ADR을 깎을 때 따르는 절차다.
ADR은 다른 문서를 작성·수정할 때 발생한 사용자 결정의 부수 기록이다.
LLM은 묻고 문서화하고, 사용자는 결정한다.

## 0. ADR의 본질

ADR(Architecture Decision Record)은 변화의 트리거가 아니다. 부수 기록이다.

> **ADR = "다른 문서를 작성·수정할 때 사용자가 내린 결정의 사유와 맥락을 기록한 영구 자료"**

ADR은 다음을 만족한다:
1. 문서 변경의 트리거가 아니다. 사용자가 ROOT_SPEC, SPEC, USECASE, EDGECASE, ISSUE, TASK를 작성·수정할 때 발생한 결정을 부수적으로 기록한다.
2. 다른 문서를 직접 변경하지 않는다. ISSUE를 자동 생성하지 않는다.
3. 다른 문서는 ADR을 인용하지 않는다. ADR INDEX가 역참조한다.
4. 폐기되지 않는다. 작성된 시점의 결정은 영구 사실로 잔존한다.
5. 결정이 갱신되면 새 ADR을 작성하고 이전 ADR을 본문에서 인용한다. 기존 ADR은 그대로 둔다.

## 1. 작성 원칙

- **LLM이 작성한다.** 본문·frontmatter는 LLM이 채운다.
- **사용자는 결정자다.** LLM은 묻고 사용자는 답한다.
- **추론 금지.** 사용자가 발화하지 않은 결정은 ADR로 만들지 않는다.
- **즉시 작성.** 결정 발생 즉시 ADR 작성. 일괄 미루지 않는다.
- 한 번에 질문은 1~2개.

## 2. 작성 트리거

다음 중 하나라도 해당하면 ADR 작성을 사용자에게 제안한다.

1. 대안이 둘 이상 명시적으로 검토됨 (사용자가 "A vs B"를 고민함).
2. 결정이 SPEC 또는 ROOT_SPEC을 변경시킴.
3. 결정이 다른 TASK·ISSUE의 진행 방식을 바꿈.
4. 결정이 ROOT_SPEC의 제약(tech_stack, 비기능 요구)을 추가/수정함.
5. 결정이 보류·기각된 대안과 그 사유를 포함함.
6. 결정이 프로젝트 가치관·우선순위·철학을 표현함.

다음 결정은 ADR 작성하지 않는다:
- 변수명·함수명 등 명명
- 파일 위치·디렉터리 구조 (관행 따른 경우)
- 한 TASK 안에서만 의미 있는 구현 디테일
- 합의된 가이드대로 진행한 것

ADR 작성 여부는 사용자에게 확인. 추론으로 자동 결정 금지.

## 3. 단계별 진행

### 1단계 — 맥락 식별
질문:
- 이 결정은 어떤 문서 작성·수정 중 발생했는가? (`context_doc`)
- 어떤 주제에 속하는가? (`tags`)

통과 기준:
- `context_doc`이 명시됨 (예: SPEC-auth-v1.2, ISSUE-0042, TASK-03, ROOT_SPEC)
- `tags`가 1개 이상 명시됨

### 2단계 — 결정 (Decision)
질문:
- 무엇을 결정했는가?
- 가치관·우선순위 결정이라면, 어떤 조건에서 어떻게 판단하는가? (구체적 조건과 예시 필수)

통과 기준:
- 결정 내용이 구체적
- 추상적 선언 금지 (예: "성능보다 가독성 우선"만으로 부족. "어떤 조건에서 어떻게"가 있어야 함)

### 3단계 — 검토된 대안 (Considered Alternatives)
질문:
- 어떤 대안들이 검토되었는가?
- 각 대안이 기각된 사유는?

통과 기준:
- 검토된 대안이 1개 이상 명시됨 (대안 없는 결정은 ADR 트리거 미달)
- 각 대안에 기각 사유 첨부

### 4단계 — 보류 (Deferred)
선택. 해당하는 경우만 작성.

질문:
- 검토했으나 이번 프로젝트 범위에 포함하지 않기로 한 아이디어가 있는가?
- 고민했으나 현 상태 유지가 최선이라고 판단한 사안이 있는가?
- 채택했으나 일부는 적용하지 않기로 한 부분이 있는가?

통과 기준:
- 해당 사안이 있으면 사유와 함께 명시
- 없으면 섹션 자체를 비움

### 5단계 — 이전 ADR 인용 (해당 시)
이 결정이 기존 ADR의 결정을 갱신하는 경우.

통과 기준:
- 본문에 이전 ADR ID를 인용하고 갱신 사유 명시
- 이전 ADR 자체는 수정하지 않음

## 4. 빈틈 패턴 (즉시 지적)

| 패턴 | 문제 | 대응 |
|---|---|---|
| 추론으로 작성 | 사용자 발화 없음 | 작성 중단 |
| 결정이 추상적 | 미래 참조 불가 | 구체적 조건·예시 강제 |
| 검토된 대안 없음 | ADR 트리거 미달 | ADR 작성하지 않음 |
| 기존 ADR을 수정 | 시간 축 결정 이력 파괴 | 새 ADR로 갱신 |
| `context_doc` 누락 | 발생 맥락 불명 | 명시 강제 |
| `tags` 누락 | 주제 검색 불가 | 명시 강제 |
| 가치관 ADR이 추상적 선언만 | 미래 판단 기준 부재 | 조건·예시 추가 |
| 다른 문서를 ADR이 직접 변경 | 본질 위반 | 별도 작업으로 분리 |

## 5. 검증 체크리스트

- [ ] frontmatter에 id, title, date, context_doc, tags가 채워짐
- [ ] 결정 내용이 구체적 (조건·예시 포함)
- [ ] 검토된 대안이 1개 이상 명시됨
- [ ] 각 대안에 기각 사유가 있음
- [ ] Deferred는 해당 시에만 작성됨
- [ ] 이전 ADR 갱신 시 본문에서 인용함
- [ ] 빈틈 패턴 8종 발견되지 않음

## 6. ADR과 다른 문서의 관계

- **ADR이 SPEC 변경을 요구할 때**: SPEC 수정은 별도 작업이다. 사용자가 SPEC을 수정하기로 결정하면, 그것은 SPEC 수정 절차(영향 범위 분석 → ISSUE 생성 → TASK 진행)로 진행된다. ADR은 그 과정의 사유 기록이다.
- **ADR이 ROOT_SPEC 변경을 요구할 때**: 동일. ROOT_SPEC 수정 절차로 별도 진행.
- **ADR은 ISSUE를 자동 생성하지 않는다.** 사용자가 후속 작업이 필요하다고 판단하면 ISSUE를 별도로 생성한다.
- **ADR을 다른 문서에서 인용하지 않는다.** 추적은 ADR INDEX의 역참조 그룹화(context_doc별, tags별)가 책임진다.

## 7. 수정 원칙

- 표현 수정(오타, 명확화)은 자유롭게 가능.
- 결정 내용이 바뀌면 새 ADR 작성. 기존 ADR은 그대로 보존.
- ADR 자체는 폐기되지 않는다. status 필드 없음.

## 8. 작성 규칙

- 정보 부족 섹션은 비우지 말고 본문에 "결정 시점에 미해결"로 명시.
- 사용자 결정 없이 임의로 채우지 않는다.
- 모든 결정은 사용자 발화에서 인용 가능해야 한다.
