# EDGECASE 작성 가이드

이 문서는 EDGECASE를 깎을 때 따르는 절차다.
EDGECASE는 SPEC을 기반으로 작성된다.
사용자는 결정하고, 작성 보조자는 묻고 문서화한다.

## 0. EDGECASE의 본질

EDGECASE는 SPEC의 계약이 정상 흐름을 벗어나는 한 가지 상황과 그에 대한 기대 동작을 기록한 문서다.

> **EDGECASE 두께 = 본질 결정론성**

SPEC이 "무엇"을 정의하고 USECASE가 "정상 흐름"을 정의한다면, EDGECASE는 "그 외 모든 경계"를 정의한다.
EDGECASE가 부족하면 LLM이 임의 판단으로 메우게 되고 외부 행동이 갈라진다.

## 1. 기본 자세

- EDGECASE는 SPEC의 계약 ID(C1, C2 등)를 직접 참조한다. SPEC 없이 EDGECASE를 쓰지 않는다.
- 한 EDGECASE = 한 트리거 = 한 파일. 여러 트리거를 묶지 않는다.
- USECASE를 참조하지 않는다. SPEC을 통해 간접 연결된다.
- 카테고리는 표준 목록(2절) 안에서만 선택한다. 새 카테고리가 필요하면 가이드를 먼저 갱신한다.
- EDGECASE 작성 중 SPEC의 누락·모호함이 발견되면 SPEC 수정 절차로 돌아간다.

## 2. 표준 카테고리

EDGECASE의 `category` 필드는 다음 중 하나여야 한다.

| 카테고리 | 의미 | 예시 |
|---|---|---|
| `input-validation` | 입력값이 형식·제약을 위반 | 잘못된 URL, 음수 TTL, 빈 문자열 |
| `state-conflict` | 데이터·자원의 상태가 부적합 | 만료된 코드, 비활성 계정, 이미 처리됨 |
| `resource-limit` | 한도·정원 초과 | 재시도 한도 초과, 발급 한도 초과 |
| `auth-denied` | 권한·인증 실패 | 비로그인, 타인 자원 접근, 토큰 만료 |
| `concurrency` | 동시 접근으로 인한 충돌 | 동시 수정, race condition, lock 획득 실패 |
| `external-failure` | 외부 의존(시스템·네트워크) 실패 | DB 연결 끊김, 외부 API 타임아웃 |

새 카테고리가 필요하다고 판단되면 이 가이드를 먼저 갱신한다. 임의 카테고리 사용 금지.

## 3. 단계별 진행 (게이트 방식)

### 1단계 — 식별
질문:
- 어떤 SPEC의 어떤 계약에서 발생하는가?
- 어떤 카테고리에 속하는가?

통과 기준:
- 관련 SPEC과 계약 ID가 명시됨
- 카테고리가 표준 목록에서 선택됨

### 2단계 — 트리거 정의
질문:
- 무엇이 이 상황을 발생시키는가?
- 가능한 입력·상태의 구체 예시는?

통과 기준:
- 트리거가 검증 가능한 형태 (테스트로 재현 가능)
- 추상적 표현("뭔가 잘못된 경우") 금지
- 가능하면 구체 예시 1개 이상 포함

### 3단계 — 기대 동작 정의
질문:
- 시스템은 어떤 응답을 반환하는가? (실패 모드, 에러 코드)
- 부수 효과는 무엇인가? (DB 변경, 로깅, 상태 전이)
- 부수 효과가 일어나지 않아야 하는 것은? (예: 무효 데이터 저장 안 됨)

통과 기준:
- 응답이 SPEC 계약의 실패 모드 중 하나로 매핑됨
- 일어나는 일과 일어나지 않는 일이 둘 다 명시됨
- 번호 매김으로 단계 결정론성 확보

### 4단계 — 검증 방법
질문:
- 이 EDGECASE를 어떻게 테스트로 확인하는가?
- 단위 테스트인가, 통합 테스트인가?

통과 기준:
- 테스트 종류와 검증 항목이 명시됨
- 코드 작성 시 그대로 테스트 케이스로 번역 가능한 수준

## 4. 빈틈 패턴 (즉시 지적)

| 패턴 | 문제 | 대응 |
|---|---|---|
| 트리거가 추상적 | 재현 불가 | 구체 예시 강제 |
| 실패 모드가 SPEC에 없는 것 | SPEC 미정의 실패 | SPEC 수정 절차 |
| "기대 동작"에 일어나지 않는 일 누락 | 부분 명세 | 부정 조건도 명시 |
| 카테고리가 표준 목록 밖 | 분류 일관성 파괴 | 가이드 갱신 또는 표준 사용 |
| 여러 트리거를 한 EDGECASE에 묶음 | 추적성 파괴 | 분리 |
| 검증 방법 없음 | 코드 번역 불가 | 테스트 정의 강제 |
| USECASE 참조 | 결합 발생 | 제거. SPEC을 통해 간접 연결 |
| 근거(rationale) 없음 | 사후 "왜 이렇게?" 불명 | 근거 작성 |

## 5. 검증 체크리스트

- [ ] frontmatter에 id, title, spec_ref, contracts, category, status가 채워짐
- [ ] 카테고리가 표준 목록(6종) 안의 값
- [ ] 트리거가 검증 가능하고 구체 예시 포함
- [ ] 기대 동작에 일어나는 일과 일어나지 않는 일이 둘 다 명시됨
- [ ] 응답이 SPEC 계약의 실패 모드 중 하나
- [ ] 검증 방법(테스트 종류·항목)이 명시됨
- [ ] 근거(rationale)가 작성됨
- [ ] 빈틈 패턴 8종 발견되지 않음
- [ ] USECASE 참조 없음

## 6. 수정 원칙

- 수정 전 영향 범위 산출:
  - 이 EDGECASE를 참조하는 ISSUE
  - 이 EDGECASE에서 인용한 ADR
- SPEC의 계약 또는 실패 모드가 변경되면 이 EDGECASE도 재검토 대상.
- 수정 후 검증 체크리스트 재실행.
- 폐기 시 `status: deprecated` 표시. 본문 잔존. 소속 SPEC major 변경 시 정리.

## 7. 작성 규칙

- 정보 부족 섹션은 비우지 말고 "열린 질문"으로 분리한다.
- 사용자 결정 없이 임의로 채우지 않는다.
- 모든 결정은 사용자 발화, ROOT_SPEC, 또는 SPEC에서 인용 가능해야 한다.
- SPEC과 충돌하면 EDGECASE를 고치지 말고 SPEC 수정 절차로 돌아간다.
